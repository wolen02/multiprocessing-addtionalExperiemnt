# Python 멀티프로세싱 성능 실험

`ProcessPoolExecutor`를 사용해 CPU 연산 작업을 병렬로 처리하고, **worker 수**와 **batch size**에 따른 실행시간 차이를 비교한 실험입니다.

## 실험 목적

- 프로세스 수를 늘렸을 때 실행시간이 얼마나 달라지는지 확인
- 같은 작업량에서 작업 묶음 크기(batch size)가 성능에 미치는 영향 확인

## 환경 및 방법

- 실행 환경: Linux (Microsoft 하이퍼바이저 기반), Intel Core i5-1135G7, 4코어/8스레드, 메모리 7.6 GiB
- Python `concurrent.futures.ProcessPoolExecutor` 사용
- 총 작업 5,000개, 작업당 반복연산 5,000회 → 매 측정당 총 **25,000,000회**
- 조건별 30회 반복 측정 (`time.perf_counter()` 사용)
- 각 반복에서 프로세스 풀을 새로 생성하고 종료함
- worker 비교에서는 batch size=2, batch 비교에서는 worker=4로 고정
- 전체 실행시간 및 시스템 정보는 `/usr/bin/time -v`로 별도 측정

## 실험 1. Worker 수에 따른 실행시간

| Worker | 평균 실행시간 (초) | 표준편차 (초) | 1 worker 대비 가속비 |
|---:|---:|---:|---:|
| 1 | 5.220 | 0.790 | 1.00x |
| 2 | 3.067 | 0.377 | 1.70x |
| 4 | 2.490 | 0.475 | 2.10x |
| 8 | 2.373 | 0.455 | 2.20x |

worker=8에서 실행시간이 가장 짧았지만, worker=4에서 8로 늘렸을 때 추가 개선 폭은 크지 않았습니다.

## 실험 2. Batch size에 따른 실행시간

| Batch size | 제출 작업 수 (매 반복) | 평균 실행시간 (초) | 표준편차 (초) |
|---:|---:|---:|---:|
| 2 | 2,500 | 2.519 | 0.373 |
| 10 | 500 | 2.525 | 0.559 |
| 50 | 100 | 2.384 | 0.337 |
| 100 | 50 | 2.490 | 0.490 |

이번 측정에서는 batch size 50에서 평균 실행시간이 가장 짧았습니다. 다만 설정 간 실행시간 차이에 비해 반복 측정의 편차도 있으므로 **50이 항상 최적이라고 단정하지는 않았습니다.**

### 시스템 측정에서 관찰한 변화

| Batch size | context switch (30회 실행 합계 측정) |
|---:|---:|
| 2 | 475,127 |
| 10 | 85,999 |
| 50 | 19,195 |
| 100 | 10,943 |

배치 크기가 커지면서 제출 작업 수와 context switch 수가 함께 감소했습니다.

## 실행 방법

```bash
python src/batchProcessing.py 4 50
```

첫 번째 인자는 worker 수, 두 번째 인자는 batch size입니다. 본 실험에서는 `2, 10, 50, 100`처럼 총 작업 수(5,000)를 나누어떨어지게 하는 batch size를 사용했습니다.

Linux에서 별도 시스템 측정 파일 저장:

```bash
/usr/bin/time -v -o system.txt python src/batchProcessing.py 4 50 > result.txt
```

## 코드 및 데이터

- `src/batchProcessing.py`: batch size를 명령행에서 입력받을 수 있도록 변경한 실험 코드
- `src/batchProcessing_original.py`: 초기 worker 수 비교에 사용한 원본 코드
- `results/workers/`: worker 수 비교, 조건별 출력 및 시스템 측정 원본
- `results/batch_sizes/`: batch size 비교, 조건별 출력 및 시스템 측정 원본

## 한계 및 배운 점

- 반복 실행 초반과 후반의 실행시간 차이가 관찰되었습니다. CPU 동작 상태나 가상화 환경 등 외부 요인을 완전히 통제하지 못했습니다.
- 프로그램의 `오버헤드 시간`은 `전체 실행시간 - (각 작업의 연산시간 합계 / worker 수)`로 계산한 **추정 잔여시간**입니다. 순수한 IPC/프로세스 생성 비용은 아닙니다.
- `/usr/bin/time`의 CPU 사용률과 메모리 수치는 전체 자식 프로세스의 사용량 합계라고 단정하지 않았습니다.
- 실제 웹캠 영상의 실시간 처리속도를 측정한 실험이 아니라, 기존 프로젝트의 병렬처리 구조를 CPU 배치 연산으로 단순화한 성능 실험입니다.

## 정리

worker 수를 늘리면 처리시간이 감소했지만 개선 폭은 점차 작아졌습니다. batch size를 크게 하면 제출 작업 수와 문맥 전환 횟수가 줄었지만, 실행시간이 반드시 계속 감소하지는 않았습니다. **병렬처리에서는 프로세스 수와 작업 분할 단위를 함께 고려해야 한다는 점**을 배웠습니다.
